# Load test — capacity report (2026-09-22)

**Question asked:** how many concurrent users does the deployed stack handle?

**Short answer:** about **100 concurrent editors** for browsing/editing traffic, but the
AI job pipeline is already losing **28% of jobs at 50 concurrent users**. At 200 the API
collapses (45.7% errors, 30 s median). The limit is **not CPU, not RAM, not the AI
vendors, and not Postgres** — every machine sat below 15% utilisation while 85% of
requests were failing. The limit is a **15-connection SQLAlchemy pool per process**, a
default the code never overrides.

Nothing was changed in the application code as a result of this test. This report
describes what to change and why.

### Why `enterprise` accounts

A fake analysis still bills real token counts (~48k tokens per 8 s clip). On `pro` /
`studio` / `max` plans the seeded users hit `402 limit_reached` after roughly 7 / 15 / 53
runs and stop generating load, which measures the billing cap rather than the stack.
`enterprise` removes the token ceiling. The side effect is that **plan-level
per-user job-concurrency limits were never exercised** — see Risks.

## 3. What saturated first, and why

### The bottleneck: a 15-connection database pool per process

`backend/packages/db/session.py` creates the engine without any pool arguments:

```python
return create_async_engine(
    settings.database_url,
    pool_pre_ping=True,
    connect_args={"prepared_statement_cache_size": 0},
)
```

With no `pool_size` / `max_overflow`, SQLAlchemy applies its defaults:
`pool_size=5`, `max_overflow=10`, `pool_timeout=30` — **15 connections per process, then
a 30-second wait, then a `TimeoutError`**. The API and the worker share this one factory.

Meanwhile `WORKER_MAX_JOBS=30` tells arq to run 30 jobs at once per worker replica. Job
16 onward has no connection to take. The two settings contradict each other and nothing
in the code reconciles them.

**Four independent pieces of evidence:**

1. **Worker tracebacks at 50 VUs** (17:23:01–17:23:40, 24 in a row):

   ```
   sqlalchemy.exc.TimeoutError: QueuePool limit of size 5 overflow 10 reached,
   connection timed out, timeout 30.00
    30.00s ! a370f1f1…:analyze_dub_video_local failed, TimeoutError: QueuePool limit…
   ```

2. **API at 200 VUs** — 1006 Railway-edge 5xx responses (85.3% of edge traffic) with a
   p50 of exactly 30 000 ms: the `pool_timeout` value, verbatim.

3. **A live probe taken while the 200-VU stage was running** — the decisive one:
   - `GET /health` (touches no database) → **200 in 0.14 s**
   - `GET /billing/plans` (touches the database) → **200 in 18.3 s, then 29.3 s**

   The process was healthy and responsive. Every request that needed a database
   connection was queuing behind the pool.

4. **Connection counts match the arithmetic.** The sampler recorded a maximum of
   **54 connections** on the Postgres server, with at most **9 actually executing a
   query**. Expected: 1 API process × 15 + 2 worker processes × 15 = 45, plus the
   sampler's own and a few admin connections. Postgres was holding idle connections
   pinned by the application, not working.

### Consequence 1 (worse than the latency): jobs that hang forever

When a worker task dies on a pool timeout, the `core.jobs` row is **never written to a
terminal status**. It stays `queued` / `running` indefinitely, and the client keeps
polling `GET /jobs/{id}` forever.

The mechanism is in `backend/services/worker/tasks.py`. Every task's failure handler
begins with:

```python
except Exception as exc:
    ts = await _tenant_session(tenant_slug)   # ← needs the pool that just timed out
    ...
    await _update_job(job_id, "error", ...)   # ← never reached
```

`_tenant_session()` and `_update_job()` both draw from the same exhausted pool, so the
error handler blocks for another 30 s and raises before it can record the failure. **The
failure path depends on the resource whose exhaustion caused the failure.**

Measured impact: **22 of 78 jobs (28%) at 50 VUs** and **72 of 124 (58%) at 100 VUs**
never reached a terminal state within the 600 s timeout. Those rows only changed status
when k6 called `DELETE /videos/{uid}` at end of session, which stamped them
`"cancelled by user"`. In production a user would watch a spinner forever, and the logs
would blame the user for cancelling something they never cancelled.

### Consequence 2: the budget guard fails open

The logs also show `llm_access_check_failed` warnings — the token-budget guard could not
reach the database and **allowed the call through**. When the pool is exhausted, spending
limits stop being enforced. In production, with real vendors, that is a billing exposure.

### What was *not* the bottleneck

| Candidate | Verdict | Evidence |
|---|---|---|
| CPU | Never | 1.20 of 8 vCPU peak (lt-api @100); 0.17 during the collapse |
| Memory | Never | 655 MB of 8 GB peak, anywhere |
| Postgres capacity | Never | 0.22 vCPU peak, 198 MB, ≤9 active queries |
| Redis | Never | 0.01 vCPU, 43 MB, ≤11 clients |
| Vendor rate limits | Never | `starts_refused = 0` in **every** stage. Peak `noey:vl:gemini:flash:req` window = **28 requests/min** against a 1000 ceiling (2.8%). No `waiting_slot` step ever observed. |
| arq queue capacity | Reached but not causal | arq in-progress peaked at **61** (the 2 replicas × `WORKER_MAX_JOBS=30` ceiling) with a queue depth up to 91 — but those slots were occupied by jobs *blocked on the pool*, not by jobs doing work |

The vendor semaphores in `packages/billing/vendor_limits.py` never had a chance to
engage. Whatever `GEMINI_RPM_FLASH` and `GEMINI_TPM_FLASH` are set to, this test could
not measure them — the pool ran out first.

### Secondary observation: polling dominates the traffic

`GET /jobs/{id}` was **20 748 of 27 228 requests (76%)** at 100 VUs. A 2-second poll
interval per in-flight job is the single largest source of API load, and every one of
those polls takes a database connection.

## 4. How many users at once

### Editing only (browse projects, edit a timeline, scrub preview, no AI run started)

**~100 concurrent — comfortably, today.** At 100 VUs: 31.8 req/s, 0.01% errors, p95
834 ms, and the API used 0.58 of 8 vCPU on average.

The 200-VU failure was the connection pool, not the machine. With the pool fixed, one API
replica should hold several hundred editing-only users; the CPU headroom says so, but
that number is a projection, not a measurement — re-run stage C after the fix to confirm.

### Users starting AI jobs

**~30 concurrent in-flight AI jobs today, and even that loses 28% of them.** Job
throughput plateaued at **≈4 completed jobs per minute (~240/hour)** and *fell* as load
rose — the classic shape of a saturated resource, not a busy one.

For comparison, with fake 75-second jobs the pipeline *should* deliver
`60 slots ÷ 75 s = 48 jobs/min`. It delivered 4. **Twelve times below its own design
point**, entirely because of the pool.

After the fix, the ceiling becomes `worker replicas × WORKER_MAX_JOBS ÷ job duration`.
With the recommended 2 × 20 slots and a 75–120 s job, that is **20–32 jobs/min
(1 200–1 900/hour)** — but see the token-quota arithmetic below, which binds first.

**Translating jobs/min into "users":** if an active creator starts one AI run every
5 minutes, 20 runs/min supports roughly **100 simultaneously active AI-using creators**.
Halve the assumed interval and halve the answer. This ratio is the number to revisit as
real usage data arrives; everything else in this report is measured.

## 5. Recommended settings

### Code changes (not applied — these are proposals)

1. **`backend/packages/db/session.py` — size the pool explicitly.** This is the whole
   finding. Suggested shape: a pool that is at least as large as the concurrency the
   process is configured to run (the worker needs ≥ `WORKER_MAX_JOBS` connections), a
   modest overflow, and a **short `pool_timeout` (≈10 s, not 30)** so an overloaded
   system fails fast and visibly instead of pretending to work for half a minute.
   Different values for API and worker, since their concurrency differs.

2. **Guarantee a terminal job row.** The failure handler in
   `backend/services/worker/tasks.py` must be able to write `error` even when the pool is
   exhausted — e.g. a small dedicated connection reserved for status writes, a
   `NullPool` engine used only by the failure path, or an arq `after_job_end` hook that
   stamps any non-terminal row. Today a user can wait forever and the log blames them.

3. **Reduce `GET /jobs/{id}` pressure.** 76% of all traffic. Options: server-sent events
   or long-polling, a longer interval that backs off while a job is known to be long-running,
   or serving job status from Redis without touching Postgres.

### Deployment settings

| Setting | Now | Recommended | Why |
|---|---|---|---|
| `WORKER_MAX_JOBS` | 30 | **20** | Must not exceed the per-process pool. 20 is comfortably servable and still gives 40 in-flight jobs across 2 replicas. |
| Worker replicas | 2 | **2** | 40 in-flight jobs ≈ 20–32 jobs/min. Scale to 3–4 only after the pool fix and after the Gemini quota is raised. |
| API processes | 1 uvicorn process × 1 replica | **1 process × 2 replicas** | One process handled 100 VUs on 0.58 vCPU. The second replica buys redundancy and rolling deploys, not throughput. Adding `--workers` multiplies pools — count connections if you do. |
| API/worker machine size | 8 vCPU / 8 GB | **Reduce** | Peak use was 1.20 vCPU and 655 MB. These containers are 6–10× oversized. |
| Postgres size | 8 vCPU / 8 GB | **Keep or reduce** — but raise `max_connections` | 0.22 vCPU and 198 MB peak. The constraint is connection *slots*, not size. Target ≥200 `max_connections`, or put Railway's Postgres connection pooling (PgBouncer) in front and point the app at the pooled endpoint. |
| Redis | 8 vCPU / 8 GB | **Reduce** | 0.01 vCPU, 43 MB, 11 clients. Wildly oversized. |

**Connection budget after the change** (worked example): API 2 replicas × 25 = 50;
worker 2 replicas × 25 = 50; total 100 plus admin/monitoring headroom → `max_connections`
of 200 is comfortable.

### Gemini quota to request

This test could not measure the vendor limits, so the numbers below are arithmetic from
measured token usage, not observations.

- **Requests:** measured peak 28 req/min while completing ~4 jobs/min → roughly
  **7 Gemini requests per completed run**. At a target of 20–48 runs/min that is
  **140–340 RPM**. With 2× headroom, request **≥700 RPM** for the flash family. The
  configured `GEMINI_RPM_FLASH=1000` is therefore adequate *if the real Google-side quota
  matches it*.
- **Tokens — this is the binding one.** A fake analysis of an 8-second clip billed
  **~48k tokens**. At 20 runs/min that is **~1.0M tokens/min**, which is exactly
  `GEMINI_TPM_FLASH=1000000`. **The token ceiling binds at ~20 runs/min, before the
  request ceiling and before the worker slots.** Real clips are longer than 8 seconds, so
  real token use will be higher still. To sustain 40–48 runs/min, request
  **≥2.5M TPM** and raise `GEMINI_TPM_FLASH` to match — otherwise the practical ceiling
  is ~20 runs/min regardless of how many workers are running.

## 6. Remaining risks — what this test did *not* measure

1. **Real Gemini latency and quota behaviour.** Fake mode returns after a fixed ~75 s
   ±30%. Real calls vary far more, can return 429/503, and retry logic then multiplies
   load. The vendor semaphores were never exercised.
2. **Real ElevenLabs behaviour**, likewise (`ELEVENLABS_MAX_CONCURRENCY=5` untested).
3. **Per-plan job-concurrency limits.** Everything ran on `enterprise`, which skips plan
   reservation (`run_reserved unlimited=true` in the logs). The `pro` / `studio` / `max`
   concurrency caps and the 402 paths are unmeasured. To measure them, reseed with
   `--plans pro,studio,max` and accept that accounts exhaust their token window.
4. **Browser-side rendering load is not in these numbers at all.** The web and desktop
   clients render on the user's own machine (WebCodecs / the local Python sidecar). None
   of it reaches the API, so it neither appears here nor limits server capacity — but it
   does mean a user's experience can be poor while every server metric looks fine.
5. **Large file uploads.** k6 sent small proxy files. Real HEVC uploads and
   `transcode_for_web` are the one genuinely CPU-heavy path
   (`WORKER_TRANSCODE_CONCURRENCY=2`) and were not stressed.
6. **Everything past 200 VUs is unknown.** The ramp stopped at the stop rule; 400 and 800
   were never run.
7. **Single-region.** Load came from one region into one region. Real users are spread
   out; TLS handshakes and latency will differ.
8. **The pool fix is unverified.** No code was changed, so no number in section 5 has
   been demonstrated. Re-run stages B and C after the fix.

## 8. Current state — what was stopped

**Nothing was deleted.** To stop the meter without destroying anything:

- `lt-runner` — **deployment removed**, no active deployment. It cannot generate load.
- `lt-api` — **deployment removed**, no active deployment. `lt-api-loadtest.up.railway.app`
  no longer answers. The service, its domain and all 28 variables are intact.
- `lt-worker` — **deployment removed**, no active deployment.
- `Postgres-35rd` and `Redis-W4zq` — **left running**, because they hold the test data and
  the seeded accounts. They are the only services still costing anything, and their volumes
  would keep costing even if stopped.

Two things worth knowing about how that was done:

1. **Railway does not allow 0 replicas.** `railway scale <region>=0` does not scale to
   zero — it *removes* that region, and Railway then falls the service back to a default
   region (`us-west2`) with 1 replica. The GraphQL API rejects `numReplicas: 0` outright
   (`Error in numReplicas - Invalid input`). The only non-destructive stop is removing the
   deployment. Region configuration was restored afterwards, so `lt-api`, `lt-worker` and
   `lt-runner` are back to `asia-southeast1` at 1 / 2 / 1 replicas respectively, ready for a
   redeploy if the test is repeated.
2. A side effect of those scale attempts was that Railway queued rebuilds of all three
   services. Those builds were cancelled and their deployments removed; **`lt-runner`
   never re-ran the load test**, and no result in this report came from them.

**To repeat the test:** redeploy `lt-api` and `lt-worker`, then deploy `lt-runner` — but
note that `lt-runner`'s variables are still set to the last (burst) stage
(`RAMP=40, RAMP_SEC=5, IDLE_SEC=0`) and must be reset for a full ramp.
