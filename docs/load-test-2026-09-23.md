# Load test — after the pool fix (2026-09-23)

**Question asked:** did the changes made after the 2026-09-22 report remove the
bottleneck, and where is the ceiling now?

Same environment, same script, same fake AI, same seeded accounts as
`docs/load-test-2026-09-22.md` — read that one first; this is the re-run, not a
new investigation.

---

## What changed between the two runs

| | Before | After |
|---|---|---|
| Database pool per process | SQLAlchemy default 5 + 10, 30 s timeout | `DB_POOL_SIZE` / `DB_MAX_OVERFLOW` / `DB_POOL_TIMEOUT_SEC` — API 20 + 10, worker 40 + 20, 10 s |
| API processes | 1 uvicorn process | `API_WORKERS=4` (migrate + seed serialised by a Postgres advisory lock) |
| `GET /jobs/{id}` | always read `core.jobs` | Redis first (`packages/db/job_cache.py`); Postgres on a miss, a foreign tenant, or a running job old enough for the stale reaper |
| Terminal job status | wrote through the pool that had just failed | falls back to a `NullPool` lifeline engine |
| Connection held during an AI call | yes, for the whole call | released at the three long ones (`_release_connection`) |
| `WORKER_MAX_JOBS` | 30 | 30 (unchanged — the pool now covers it) |

Machine sizes, worker replicas and the fake-AI delays are unchanged, so the
stages compare directly.

## Results

### Stage A — 50 virtual users

| | 2026-09-22 | 2026-09-23 |
|---|---|---|
| Jobs completed | 56 | **159** |
| Jobs timed out | **22 (28%)** | **0** |
| Jobs completed per minute | 3.92 | **15.9** |
| HTTP req/s | 14.6 | **29.1** |
| HTTP p95 | 493 ms | **190 ms** |
| HTTP error rate | 0.00% | 0.02% |
| `GET /jobs/{id}` p95 | 516 ms | **71 ms** |
| Job run time p50 | 82 s | 78 s |
| Queue wait p50 | 2.4 s | 2.5 s |
| Worker `QueuePool` timeouts in the logs | 24 | **0** |

Four times the throughput, and nothing lost. The fake model call takes ~75 s, so
a 78 s p50 run time means the pipeline is now spending its time waiting on the
model and almost nothing else.

`GET /jobs/{id}` was 6,150 of 17,432 requests (35%, down from 76% of a much
slower run) and answers in 55 ms at the median without taking a database
connection at all.

### Stage B — 100 virtual users

| | 2026-09-22 | 2026-09-23 |
|---|---|---|
| Jobs completed | 52 | **319** |
| Jobs timed out | **72 (58%)** | **0** |
| Jobs completed per minute | 3.64 | **31.4** |
| HTTP req/s | 31.8 | **58.1** |
| HTTP p50 / p95 | 436 / 834 ms | **88 / 191 ms** |
| HTTP error rate | 0.01% | **0.00%** |
| `GET /jobs/{id}` p50 / p95 | 476 / 851 ms | **55 / 72 ms** |
| Job run time p50 | 122 s | **76 s** |
| Queue wait p50 / p95 | 2.8 / 3.6 s | 2.5 / 41.7 s |
| Worker `QueuePool` timeouts | many | **0** |
| Lifeline fallbacks used | n/a | 0 (the pool never ran out) |

Eight and a half times the throughput with nothing lost, and the job run time
is back down to the fake model's own latency: at 100 users the previous build
was taking 122 s for a 75 s model call because the rest was spent waiting for a
connection.

The one number that grew is queue wait at p95 (41.7 s). That is the arq queue
doing its job — 100 users start more work than 30 worker slots run at once, so
some jobs wait for a slot instead of being dropped. Waiting is the correct
behaviour; the previous build's 3.6 s p95 looked better only because it was
losing 58% of the jobs instead of queuing them.

Resource use during this stage (limit 8 vCPU / 8 GB per service):
`lt-api` 0.23 vCPU average, 1.31 peak, 2.1 GB peak across its four processes;
`lt-worker` 0.08 average, 0.40 peak, 0.69 GB. Still nowhere near the machines.

## Method

Unchanged from the 2026-09-22 report: `lt-runner` (k6 on Railway, same region),
`LOADTEST_FAKE_AI=1`, 600 seeded `enterprise` accounts, usage windows reset
between stages. One stage per runner deployment; the summary line is read out of
the runner's logs.

The loadtest services deploy from a staged copy of `backend/`, not from git — so
`railway link` has to be run inside that folder, or `railway up` uploads its
parent and the build fails looking for the Dockerfile.
